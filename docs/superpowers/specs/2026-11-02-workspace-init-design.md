# Agent 多仓库 Worktree 开发规范：通用化与首次初始化设计

日期：2026-11-02

状态：等待书面设计复核

技能仓库：https://github.com/xiao-en-5970/agent-multi-repo-worktree-dev

## 1. 背景

现有分支维度开发方法已经证明：一次需求使用一个分支名，在同一目录下为涉及的仓库创建 worktree，并用 `tmp/README.md` 支持交接，可以有效隔离并行需求。

通用化还需要解决两个问题：

1. “一键初始化”只覆盖分支开发目录，不覆盖首次使用时的根目录、`main/` 和主 checkout 准备。
2. 通用流程不能绑定个人路径、特定仓库清单、内部部署规则或客户端偏好。

本次改造将建设完全通用的“Agent 多仓库 Worktree 开发规范”，并增加独立的首次工作区初始化流程。

## 2. 目标

- 首次使用必须显式提醒用户指定 `main` 基座目录，并指定或确认 `WorkTree` 基座目录。
- `main` 基座目录直接存放所有登记项目的主分支 checkout；`WorkTree` 基座目录存放所有分支开发目录。
- 两个基座目录必须同级，工作区根目录由它们的共同父目录推导，分支开发目录统一位于 `WorkTree/<branch>/`。
- 同时支持接管已有目录和创建新工作区，允许部分仓库已存在、部分缺失。
- 初始化可重复执行，不覆盖冲突、不重复 clone、不重建已有 worktree。
- 技能仓库不包含个人或组织专属路径、仓库名、服务名、环境分支、部署规则及客户端偏好。
- 分支开发初始化和首次工作区初始化拥有明确、不同的触发入口。
- 部署 test、UAT 或生产前，自动追踪项目真实 CI/CD 配置及其脚本，不根据习惯假定分支、tag 或触发方式。
- 技能使用独立 Git 仓库维护，设计、实施和验证记录可以版本化。

## 3. 非目标

- 首版不开发独立 CLI 或包管理器发布流程；由 agent 按配置执行幂等步骤。
- 不自动扫描并接管用户机器上的任意 Git 仓库。
- 不统一不同项目的主分支、测试分支或部署方式。
- 不自动移动目录、切换分支、拉取、安装依赖或部署环境。
- 不修改已有 worktree 的分支、提交和文件内容。
- 不在技能仓库中提供任何个人或组织专属的兼容层。

## 4. 方案选择

比较过三种方式：

| 方案 | 结果 |
|---|---|
| 仅给现有文档追加初始化章节并参数化路径 | 否决：仍然容易保留特定项目耦合 |
| 完全通用的技能 + 工作区外置规则 | 采用：技能独立复用，项目规则不进入技能仓库 |
| 通用技能 + 技能仓库内的组织扩展包 | 否决：扩展包仍会引入组织专属内容 |

## 5. 仓库与技能结构

技能对外名称为“Agent 多仓库 Worktree 开发规范”，英文标识为 `agent-multi-repo-worktree-dev`。

唯一维护仓库：

```text
https://github.com/xiao-en-5970/agent-multi-repo-worktree-dev
```

仓库根目录就是技能根目录：

```text
agent-multi-repo-worktree-dev/
├── SKILL.md
├── references/
│   ├── workspace-init.md
│   ├── branch-init.md
│   ├── handoff.md
│   └── deployment.md
├── templates/
│   ├── workspace-config.yaml
│   └── branch-readme.md
└── docs/
    └── superpowers/
        └── specs/
```

### 5.1 通用核心

`SKILL.md` 只保留：

- 技能触发条件与两个初始化入口的路由。
- 工作区配置发现规则。
- 一次开发 = 一个分支名 = 一个目录的模型。
- 主 checkout 与开发 worktree 的职责边界。
- 不基于环境分支开发、不反向合并的纪律。
- 写入前的确认、幂等和冲突处理原则。
- 部署前自动追踪真实 CI/CD 实现的要求。
- 对详细参考文件的按需加载指引。

### 5.2 参考文件

- `workspace-init.md`：首次初始化、接管、补充 clone、校验和错误处理。
- `branch-init.md`：分支命名、基线确认、逐仓 worktree 创建及回报。
- `handoff.md`：分支 README 模板、更新时机和交接自检。
- `deployment.md`：自动定位并追踪项目真实 CI/CD 配置、include、部署脚本和校验逻辑；以代码证据确认环境触发方式，无法确定时停止并询问。

### 5.3 项目规则外置

个人或组织规则由技能之外的工作区指令、仓库指令或用户当次指令提供。技能可以读取并遵循这些规则，但不复制进技能仓库。

未提供项目部署规则时，技能只执行通用安全检查并询问，不生成特定环境分支、tag 格式、依赖安装命令或客户端命名要求。

## 6. 工作区配置

配置文件固定为：

```text
<workspace>/.branch-worktree/config.yaml
```

工作区根目录由配置文件位置推导，不保存本机绝对路径，从而使配置本身不绑定特定用户。

首版字段：

```yaml
version: 1
mainDir: main
worktreeDir: WorkTree

repositories:
  - name: example-api
    path: api
    url: git@example.com:team/example-api.git
    defaultBranch: main
```

字段语义：

| 字段 | 必填 | 语义 |
|---|---|---|
| `version` | 是 | 首版只能为 `1`，其他版本停止并报告不支持 |
| `mainDir` | 是 | 用户指定的主 checkout 基座目录；必须是工作区内的单级相对目录 |
| `worktreeDir` | 是 | 用户指定或确认的分支工作区基座目录；必须是工作区内的单级相对目录 |
| `repositories` | 是 | 登记仓库列表；允许空列表，但初始化结果必须提示尚未登记仓库 |
| `name` | 是 | 稳定的逻辑名称，在同一配置内唯一 |
| `path` | 是 | 仓库在 `mainDir` 下的单级相对目录，在同一配置内唯一 |
| `url` | 否 | 缺失仓库的 clone 来源；已有仓库不以此覆盖 remote |
| `defaultBranch` | 否 | 开发基线；缺省时探测，探测失败则询问 |

安全约束：`mainDir`、`worktreeDir` 和 `path` 不得为绝对路径，不得包含 `..`，不得逃逸工作区；`mainDir` 与 `worktreeDir` 不得相同，也不得指向 `.git` 或 `.branch-worktree`；`path` 不得指向 `.git` 或 `.branch-worktree`。

## 7. 配置发现

按以下顺序解析：

1. 用户明确提供工作区根目录或配置文件。
2. 从当前目录向上查找 `.branch-worktree/config.yaml`。
3. 未找到配置时进入首次初始化，先展示首次使用提醒并询问 `main` 与 `WorkTree` 基座目录，不使用当前目录或任何个人默认路径代替用户选择。

找到多个候选配置时，以离当前目录最近者为准；用户指定的配置优先。解析失败时停止写操作并报告具体字段，不回退到任何内置项目默认值。

## 8. 首次工作区初始化

触发方式：用户明确说“初始化多仓工作区”，或当前任务需要工作区但没有可用配置。

### 8.1 首次使用硬提醒

第一次使用且没有可用配置时，必须先向用户展示：

> 第一次使用 Agent 多仓库 Worktree 开发规范，请先指定一个目录作为 `main` 基座目录，并指定或确认一个 `WorkTree` 基座目录。`main` 目录直接存放所有项目的主分支 checkout（`main`、`master` 等）；`WorkTree` 目录存放所有分支开发目录。两个目录必须同级，后续开发 worktree 都以 `main` 中的主 checkout 为基座创建。

提醒后必须等待用户提供或明确确认两个目录。未提供或未确认任一目录时停止，不使用当前目录、技能仓库目录或任何内置路径代替。

用户给出两个基座目录后，先展示推导结构并请求确认：

```text
<workspace>/                      # 两个基座目录的共同父目录
├── .branch-worktree/
│   └── config.yaml
├── <mainDir>/                    # 用户指定的 main 基座目录
│   ├── project-a/                # 项目主分支 checkout
│   └── project-b/
└── <worktreeDir>/                # 用户指定或确认的 WorkTree 基座目录
    └── <branch-name>/            # 一次开发的分支目录
        ├── project-a/
        └── tmp/
```

`mainDir` 和 `worktreeDir` 分别是两个用户确认路径的最后一级目录名，`workspace` 是它们的共同父目录。两个路径不在同一父目录时要求重新选择。用户未确认推导结构前，不创建目录或配置。

### 8.2 输入

- `main` 基座目录，不能直接指向某个项目仓库。
- `WorkTree` 基座目录，不能与 `main` 基座目录相同或互相嵌套。
- 初始化模式：接管已有目录、新建工作区，或两者混合。
- 仓库登记来源：用户提供的清单、已有 `main` 基座目录下经确认的 Git checkout，或两者组合。

### 8.3 执行顺序

1. 将 `main` 与 `WorkTree` 基座目录解析为绝对路径，验证二者同级且互不嵌套，推导工作区根目录、`mainDir` 和 `worktreeDir`，再验证可写性、路径冲突和 Git 可用性。
2. 展示目标结构、登记仓库和将执行的写操作；clone 或任何覆盖性操作必须单独确认。首版不提供目录移动或覆盖操作。
3. 创建 `.branch-worktree/`、`main` 基座目录和 `WorkTree` 基座目录，生成或更新配置。
4. 逐仓处理：
   - 路径已存在且为有效 Git checkout：保留并登记，不切换分支、不 pull、不改 remote。
   - 路径已存在但不是有效 Git checkout：标记冲突并跳过该仓，不覆盖。
   - 路径不存在且提供 URL：经用户确认后 clone。
   - 路径不存在且没有 URL：标记为待补充，不猜测远端。
5. 对每个有效仓库读取当前分支、remote HEAD 和 worktree 列表；显式配置的 `defaultBranch` 优先于探测值。
6. 复核配置和目录状态，输出已登记、已 clone、已跳过、冲突和待补充清单。

### 8.4 幂等性

- 已有有效仓库不重复 clone。
- 已有配置与输入一致时不重写。
- 已有配置与输入冲突时先报告差异并询问，不做静默覆盖。
- 单仓失败不破坏其他已完成登记，但最终结果必须明确标记为部分完成。

### 8.5 默认禁止事项

首次初始化不执行依赖安装、开发分支创建、部署、凭据读取、目录移动或现有 checkout 清理。

## 9. 分支开发初始化

原“一键初始化”更名为“分支开发初始化”。执行前必须已成功解析工作区配置。

流程为：

1. 确定所有仓库共用的分支名。
2. 确认涉及仓库及每仓基线，不基于环境分支新建开发线。
3. 创建 `<workspace>/<worktreeDir>/<branch>/tmp/`。
4. 从 `<workspace>/<mainDir>/<repo>` 创建或补充 `<workspace>/<worktreeDir>/<branch>/<repo>` worktree。
5. 已有目标 worktree 时跳过并校验其分支归属，不重建。
6. 创建 `<workspace>/<worktreeDir>/<branch>/tmp/README.md`，填实仓库矩阵、基线和状态。
7. 回报路径、基线、跳过项、阻塞项和下一步。

`mainDir` 只是主 checkout 容器名，与 Git 主分支名无关。各仓基线独立解析为 `main`、`master` 或已有开发分支。

工作区或仓库已有规范可以追加依赖安装等行为；通用技能默认不执行这些行为。

## 10. 现有工作区兼容

接管已有工作区时：

1. 在用户指定的 `main` 基座目录父级生成配置，登记该基座目录下的主 checkout。
2. 不移动主 checkout，不删除历史 worktree，不重建分支维度 worktree。
3. 不改变已有分支、remote、依赖和项目指令。
4. 工作区根目录、主 checkout 或 `WorkTree` 中的 worktree 被主动移动后，仍按 Git 规则执行 `git worktree repair`；配置可迁移不等于 Git worktree 指针会自动修复。

## 11. 部署前 CI/CD 实现追踪

用户要求部署、推进或给出 test、UAT、生产环境的部署入口时，必须自动对目标项目执行只读 CI/CD 追踪。不得因为仓库中常见某个分支名或 tag 名，就直接认定其部署用途。

### 11.1 追踪顺序

1. 读取项目指令和 CI 入口，包括实际存在的 `.gitlab-ci.yml`、`.github/workflows/`、`Jenkinsfile`、其他 CI 配置及部署目录。
2. 沿本地 include、模板、可复用 workflow、部署脚本和环境校验脚本继续追踪，直到目标环境 job 的真实执行与判定逻辑。
3. 确认目标环境的触发事件、分支或 tag 匹配规则、目标 ref、手动门禁、版本校验、所需变量及实际部署动作。
4. 核对这些规则所在的 CI 配置版本与待部署 commit；若目标 ref 上的实现不同，必须继续读取目标 ref 版本，不能用当前分支的配置代替。
5. 输出环境、CI 文件与行号、job、触发条件、目标 ref、手动门禁、证据和未解决项。涉及变量时只记录名称，不输出凭据值。

远程 include 或外部部署脚本不可访问时，将其列为证据缺口，不根据名称猜补。只读追踪不等于授权访问集群、凭据或部署环境。

### 11.2 部署纪律

- 不内置或默认任何 test、UAT、生产分支名、tag 格式、版本规则或环境推进顺序。
- 多个 job 或规则都能匹配目标环境时，列出候选及差异，由用户确认目标。
- CI 配置缺失、实现无法读取、证据冲突或目标 commit 的 CI 版本未核对时，停止部署动作并询问。
- merge、push、打 tag、触发 pipeline 等写操作前，必须另行展示从证据推导出的动作、目标 commit 和环境，并获得用户确认。
- 不得把“找到 CI 文件”当作“已经理解部署方式”；必须追踪到实际控制触发和校验的实现。

## 12. 错误处理与回报

所有写操作遵循以下回报结构：

1. 阻塞项与冲突。
2. 已完成项及可核对路径。
3. 跳过项及原因。
4. 下一步动作及需要用户提供的信息。

禁止把部分成功报告为全部完成。禁止在无法访问目标路径、无法解析配置或缺少仓库 URL 时使用个人路径和远端补齐。

## 13. 验证设计

技能改造按文档 TDD 执行：先观察未改造行为在相同场景下的失败，再写最小改动，最后用相同场景复测。

### 13.1 基线场景

- 在没有配置的新目录要求首次初始化。
- 用户只提供 `main` 基座目录，尚未提供或确认 `WorkTree` 基座目录。
- 在任意非项目专属目录要求接管两个现有仓库。
- 配置只有部分仓库存在，且一个目标路径不是 Git 仓库。
- 两个仓库分别使用 `main` 和 `master`。
- 两个仓库使用不同部署方式：一个由分支 push 触发，另一个由 tag 和手动 job 触发。
- CI 入口通过 include 和部署脚本间接决定环境分支及校验规则。
- 当前分支与目标 ref 的 CI/CD 实现不同。
- 远程 include 无法访问或 CI 证据冲突时要求部署。
- 在工作区子目录再次执行初始化和分支初始化。

记录是否出现个人路径回退、未经确认的写操作、错误部署假设、重复 clone 或遗漏冲突。

### 13.2 改造后通过条件

- 第一次使用且没有配置时，必然先出现 `main` 与 `WorkTree` 基座目录提醒及用途说明。
- 用户未指定或确认任一基座目录，或者未确认推导结构时，不产生任何写操作。
- 两个基座目录同级，新目录只在用户确认的共同父级工作区内写入。
- 分支开发目录统一位于 `<workspace>/<worktreeDir>/<branch>/`。
- 接管操作不改变已有 checkout 的分支、remote 和内容。
- 重跑无重复 clone、无重复 worktree、无配置差异。
- 非 Git 冲突被保留并显著报告。
- 部署结论来自目标 commit 的真实 CI/CD 文件、include 和脚本证据，不从分支或 tag 名称猜测。
- CI 证据缺失、冲突或版本未核对时停止部署动作。
- 未提供项目规则时不出现特定服务和客户端命名要求。
- 分支初始化使用配置解析出的同一工作区根目录。
- 技能仓库扫描不到个人绝对路径、个人标识、组织专属仓库名、服务名和内部部署规则。

若后续增加脚本，使用临时目录和本地 bare Git 仓库做真实集成测试，不依赖线上仓库或凭据。

## 14. 实施边界

先交付配置模板、技能分层和确定性操作流程。只有这些规则经场景验证稳定后，才考虑把重复命令固化为脚本。任何新增脚本都属于后续独立设计，不在本次隐式扩展。

技能仓库当前为空，本地默认分支为 `main`。设计文档在复核后提交到该仓库；实施与验证通过前不推送远端。
