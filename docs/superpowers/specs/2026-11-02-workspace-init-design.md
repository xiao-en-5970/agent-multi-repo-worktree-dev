# Agent 多仓库 Worktree 开发规范：通用化与首次初始化设计

日期：2026-11-02

状态：等待书面设计复核

技能仓库：https://github.com/xiao-en-5970/agent-multi-repo-worktree-dev

## 1. 背景

分支维度开发方法采用以下模型：一次需求使用一个分支名，在同一目录下为涉及的仓库创建 worktree，并用 `tmp/README.md` 支持交接，以隔离并行需求。

通用化还需要解决两个问题：

1. “一键初始化”只覆盖分支开发目录，不覆盖首次使用时的根目录、`main/` 和主 checkout 准备。
2. 通用流程不能绑定个人路径、特定仓库清单、内部部署规则或客户端偏好。

本次改造将建设与具体项目无关的“Agent 多仓库 Worktree 开发规范”，并增加独立的首次工作区初始化流程。

## 2. 目标

- 首次使用必须显式提醒用户指定 `main` 基座目录，并指定或确认 `WorkTree` 基座目录。
- `main` 基座目录直接存放所有登记项目的主分支 checkout；`WorkTree` 基座目录存放所有分支开发目录。
- 两个基座目录必须同级，工作区根目录由它们的共同父目录推导，分支开发目录统一位于 `WorkTree/<branch>/`。
- 同时支持接管已有目录和创建新工作区，允许部分仓库已存在、部分缺失。
- 初始化可重复执行，不覆盖冲突、不重复 clone、不重建已有 worktree。
- 技能仓库不包含个人或组织专属路径、仓库名、服务名、环境分支、部署规则及客户端偏好。
- 分支开发初始化和首次工作区初始化拥有明确、不同的触发入口。
- 部署 test、UAT 或生产前，自动追踪项目真实 CI/CD 配置及其脚本，不根据习惯假定分支、tag 或触发方式。
- 技能使用独立 Git 仓库维护，设计、实施和验证记录可以版本化。

## 3. 非目标

- 首版不开发独立 CLI 或包管理器发布流程；由 agent 按配置执行幂等步骤。
- 不自动扫描并接管用户机器上的任意 Git 仓库。
- 不统一不同项目的主分支、测试分支或部署方式。
- 不自动移动目录、切换分支、拉取、安装依赖或部署环境。
- 首次初始化不修改已有 checkout 或 worktree 的分支、提交和文件内容。
- 不在技能仓库中提供任何个人或组织专属的兼容层。

## 4. 方案选择

比较过三种方式：

| 方案 | 结果 |
|---|---|
| 仅给现有文档追加初始化章节并参数化路径 | 否决：仍然容易保留特定项目耦合 |
| 完全通用的技能 + 工作区外置规则 | 采用：技能独立复用，项目规则不进入技能仓库 |
| 通用技能 + 技能仓库内的组织扩展包 | 否决：扩展包仍会引入组织专属内容 |

## 5. 仓库与技能结构

技能对外名称为“Agent 多仓库 Worktree 开发规范”，英文标识为 `agent-multi-repo-worktree-dev`。

唯一维护仓库：

```text
https://github.com/xiao-en-5970/agent-multi-repo-worktree-dev
```

仓库根目录就是技能根目录：

```text
agent-multi-repo-worktree-dev/
├── README.md
├── SKILL.md
├── references/
│   ├── workspace-init.md
│   ├── branch-init.md
│   ├── maintenance.md
│   ├── handoff.md
│   └── deployment.md
├── templates/
│   ├── workspace-config.yaml
│   └── branch-readme.md
└── docs/
    └── superpowers/
        └── specs/
```

### 5.1 通用核心

`SKILL.md` 只保留：

- YAML frontmatter 的 `name` 与 `description`；`description` 以 `Use when` 开头，只写触发场景，不概述执行流程。
- 首次初始化、分支初始化、维护、交接和部署的入口路由。
- 工作区配置发现规则。
- 一次开发 = 一个分支名 = 一个目录的模型。
- 主 checkout 与开发 worktree 的职责边界。
- 不基于已确认的环境分支开发、不反向合并的纪律。
- 写入前的确认、幂等和冲突处理原则。
- 部署前自动追踪真实 CI/CD 实现的要求。

`README.md` 只说明安装、首次使用入口和文档导航，不复制参考文件中的流程。

### 5.2 参考文件与加载条件

| 参考文件 | 加载条件 | 内容 |
|---|---|---|
| `workspace-init.md` | 没有可用配置，或用户要求初始化工作区 | 双基座目录确认、接管、clone、校验和错误处理 |
| `branch-init.md` | 用户要求创建或补充分支 worktree | 分支与路径校验、基线确认、逐仓创建和回报 |
| `maintenance.md` | 用户要求检查、修复或清理 worktree | 状态检查、repair、保留证据和安全清理 |
| `handoff.md` | 创建分支目录、更新进度或交接 | 分支 README 模板、更新时机和完成判据 |
| `deployment.md` | 用户要求部署或提供部署入口 | 自动追踪 CI/CD 配置、include、部署脚本和校验逻辑 |

每个主题只在一个参考文件中维护完整规则；其他文件只保留链接，不复制流程。

### 5.3 项目规则外置

个人或组织规则由技能之外的工作区指令、仓库指令或用户当次指令提供。技能可以读取并遵循这些规则，但不复制进技能仓库。规则冲突时展示差异并询问，不静默覆盖安全边界。

未提供项目部署规则时，技能仍须自动追踪 CI/CD。证据充分时不再询问部署方式；证据不足或存在多种解释时才询问。merge、push、tag、pipeline 等写操作仍按对应章节单独确认。不得生成没有代码证据的环境分支、tag 格式、依赖安装命令或客户端命名要求。

## 6. 工作区配置

配置文件固定为：

```text
<workspace>/.branch-worktree/config.yaml
```

工作区根目录由配置文件位置推导，不保存本机绝对路径，从而使配置本身不绑定特定用户。

首版字段：

```yaml
version: 1
mainDir: main
worktreeDir: WorkTree

repositories:
  - name: example-api
    path: api
    url: git@example.com:team/example-api.git
    remote: origin
    defaultBranch: main
```

字段语义：

| 字段 | 必填 | 语义 |
|---|---|---|
| `version` | 是 | 首版只能为 `1`，其他版本停止并报告不支持 |
| `mainDir` | 是 | 用户指定的主 checkout 基座目录；必须是工作区内的单级相对目录 |
| `worktreeDir` | 是 | 用户指定或确认的分支工作区基座目录；必须是工作区内的单级相对目录 |
| `repositories` | 是 | 登记仓库列表；允许空列表，但初始化结果必须提示尚未登记仓库 |
| `name` | 是 | 稳定的逻辑名称，在同一配置内唯一 |
| `path` | 是 | 仓库在 `mainDir` 下的单级相对目录，在同一配置内唯一 |
| `url` | 否 | 缺失仓库的 clone 来源；已有仓库不以此改写 remote URL |
| `remote` | 否 | 基线与远端分支的读取来源；选择规则见本节下文 |
| `defaultBranch` | 否 | 默认开发基线分支；缺省时从已选 remote 探测，探测失败则询问 |

每仓 remote 按“显式 `remote` 配置 → 仓库只有一个 remote → 否则询问”选择，不默认 `origin`。配置的 remote 不存在时停止。首次初始化和分支初始化都使用这一规则。

配置校验规则：

- YAML 任意层级出现重复键、字段类型错误或未定义字段时停止，指出完整字段路径；不允许解析器静默覆盖。
- `mainDir`、`worktreeDir`、`name`、`path` 必须为非空字符串；`name` 唯一。两个基座目录名不能为 `.`，且必须不同。
- `path` 只能是单级相对目录，不能为 `.`、`tmp`、`.git` 或 `.branch-worktree`。
- `mainDir`、`worktreeDir` 和 `path` 不得为绝对路径或包含 `..`；解析符号链接后仍须位于工作区内。
- 两个基座目录不得为 `.git` 或 `.branch-worktree`。按当前文件系统语义规范化后，仓库物理路径必须唯一；大小写或符号链接导致的碰撞也算冲突。
- `defaultBranch` 在用于 Git 操作前必须通过 `git check-ref-format --branch`。
- `url` 不得内嵌密码、token 或其他秘密凭据；发现秘密凭据时停止并要求改用外部认证。

校验失败时不创建目录、不修改配置、不执行 Git 写操作。

## 7. 配置发现

按以下顺序解析：

1. 用户明确提供工作区根目录或配置文件。
2. 从当前目录向上查找 `.branch-worktree/config.yaml`。
3. 未找到配置时进入首次初始化，先展示首次使用提醒并询问 `main` 与 `WorkTree` 基座目录，不使用当前目录或任何个人默认路径代替用户选择。

找到多个候选配置时，以离当前目录最近者为准；用户指定的配置优先。解析失败时停止写操作并报告具体字段，不回退到任何内置项目默认值。

## 8. 首次工作区初始化

触发方式：用户明确说“初始化多仓工作区”，或当前任务需要创建、补充或维护 worktree 但没有可用配置。只读排查不触发初始化。

### 8.1 首次使用硬提醒

第一次使用且没有可用配置时，必须先向用户展示：

> 第一次使用 Agent 多仓库 Worktree 开发规范，请先指定一个目录作为 `main` 基座目录，并指定或确认一个 `WorkTree` 基座目录。`main` 目录直接存放所有项目的主分支 checkout（`main`、`master` 等）；`WorkTree` 目录存放所有分支开发目录。两个目录必须同级，后续开发 worktree 都以 `main` 中的主 checkout 为基座创建。

提醒后必须等待用户提供或明确确认两个目录。未提供或未确认任一目录时停止，不使用当前目录、技能仓库目录或任何内置路径代替。

用户给出两个基座目录后，先展示推导结构并请求确认：

```text
<workspace>/                      # 两个基座目录的共同父目录
├── .branch-worktree/
│   └── config.yaml
├── <mainDir>/                    # 用户指定的 main 基座目录
│   ├── project-a/                # 项目主分支 checkout
│   └── project-b/
└── <worktreeDir>/                # 用户指定或确认的 WorkTree 基座目录
    └── <branch-name>/            # 一次开发的分支目录
        ├── project-a/
        └── tmp/
```

`mainDir` 和 `worktreeDir` 分别是两个用户确认路径的最后一级目录名，`workspace` 是它们的共同父目录。两个路径不在同一父目录时要求重新选择。用户未确认推导结构前，不创建目录或配置。

### 8.2 输入

- `main` 基座目录，不能直接指向某个项目仓库。
- `WorkTree` 基座目录，不能与 `main` 基座目录相同或互相嵌套。
- 初始化模式：接管已有目录、新建工作区，或两者混合。
- 仓库登记来源：用户提供的清单、`main` 基座目录直接子级中经用户确认的 Git checkout，或两者组合；不递归扫描。

“有效 Git checkout”的判据是：`git -C <path> rev-parse --show-toplevel` 成功，且解析后的顶层目录与 `<path>` 一致。`.git` 可以是目录或 worktree 指针文件。任一基座目录自身若是 Git checkout 根，则停止并要求重新选择。

### 8.3 执行顺序

1. 将两个基座目录解析为物理路径，验证二者具有共同父目录且互不嵌套，再推导工作区根目录、`mainDir` 和 `worktreeDir`。目录不存在时先校验最近现有祖先和待创建路径，创建后重新解析；任一路径逃逸、碰撞或 Git 不可用时停止。
2. 展示目标结构、登记仓库和将执行的写操作；clone 必须单独确认。首版不移动目录，也不覆盖已有路径。
3. 创建两个基座目录并重新解析物理路径；确认未逃逸或碰撞后，再创建 `.branch-worktree/` 并生成或更新配置。
4. 逐仓处理：
   - 路径已存在且为有效 Git checkout：保留并登记，不切换分支、不 pull、不改 remote。
   - 路径已存在但不是有效 Git checkout：标记冲突并跳过该仓，不覆盖。
   - 路径不存在且提供 URL：经用户确认后 clone。
   - 路径不存在且没有 URL：标记为待补充，不猜测远端。
5. 按第 6 节选择每仓 remote，读取当前分支和 worktree 列表。`defaultBranch` 未配置时从该 remote 的 HEAD 探测；探测失败则询问，不凭分支名猜测。当前分支与 `defaultBranch` 不一致时记录“基线漂移”，不切换分支。
6. 将已确认的 `remote` 和 `defaultBranch` 写回对应仓库配置，复核目录状态，输出已登记、已 clone、已跳过、冲突和待补充清单；未确认的字段不得填猜测值。

### 8.4 幂等性

- 已有有效仓库不重复 clone。
- 已有配置与输入一致时不重写。
- 输入为同一配置字段提供不同值时，先报告语义差异并询问，不做静默覆盖；未提供的字段保持原值。
- 任一登记仓库发生冲突、clone 失败或缺少 URL 时，最终状态为“部分完成”；不得报告为“初始化完成”。已成功登记的仓库保持原状。
- `repositories` 为空时，最终状态为“待登记仓库”；不得进入分支开发初始化。

### 8.5 默认禁止事项

首次初始化不执行依赖安装、开发分支创建、部署、凭据读取、目录移动或现有 checkout 清理。

## 9. 分支开发初始化

原“一键初始化”更名为“分支开发初始化”。执行前必须通过配置校验，且所有涉及仓库均已登记并具有有效主 checkout。

每仓 remote 按第 6 节规则选择。

流程为：

1. 确定共用分支名，用 `git check-ref-format --branch` 校验，并核对各仓命名规约。规约冲突且无法使用同一分支名时停止并询问。
2. 将分支目录解析到 `<workspace>/<worktreeDir>/<branch>/`。路径必须位于 `worktreeDir` 内，不得与 `mainDir`、`.git`、`.branch-worktree` 重叠；其父级或子级已是另一分支工作区时也停止，不自动改名。
3. 明确涉及仓库及各仓基线。默认分支基线取已选 remote 的完整 commit SHA；已有开发分支必须由用户明确指定。
4. 选择非默认分支作为基线时，先通过项目指令或 CI/CD 证据确认它不是部署环境分支；无法确认时列出候选并询问，不凭名称判断。
5. 记录各主 checkout 的当前分支、commit 和脏状态，不修改主 checkout。当前分支与 `defaultBranch` 不一致时标记“基线漂移”；默认基线仍取已选 remote 的默认分支 commit，不取主 checkout HEAD。
6. 在任何写入前，解析所有 `<branchDir>/<path>` 物理路径；目标不存在时解析最近现有祖先并校验待创建尾路径。结果必须位于 `branchDir` 内，不得与 `tmp`、`.git`、`.branch-worktree`、其他仓库路径或已有分支工作区重叠。
7. 对需要远端基线的仓库，展示已选 remote 并在确认后 fetch，记录完整 SHA。fetch 失败时停止；只有用户明确指定本地 commit 并确认其可能过旧后，才可使用该 commit。
8. 校验通过后创建 `tmp/`，再逐仓按顺序处理：目标 worktree 已存在则核对路径和分支后跳过；分支已在其他 worktree 检出则报冲突；本地分支存在则使用其当前 commit；所选 remote 唯一同名分支存在则使用该远端 commit；都不存在才从确认的默认基线新建；存在多个匹配则询问。已有分支不 reset、不 rebase。
9. 创建 `tmp/README.md`，填实仓库矩阵、基线 commit、状态和下一步；回报成功、跳过、冲突及证据。

`mainDir` 只是主 checkout 容器名，与 Git 主分支名无关。各仓默认分支独立解析。

只有工作区、仓库指令或用户明确要求时，才执行依赖安装等附加动作；执行前说明命令、目录和影响。

### 9.1 交接记录

`tmp/README.md` 至少包含：目标、分支名、仓库矩阵、每仓基线与当前 commit、当前阶段、验证证据、阻塞项及负责人、下一步、关键决策。

状态只使用“未开始、进行中、阻塞、完成、不适用”。“完成”必须附 commit、命令结果或部署证据；“阻塞”必须说明缺什么、由谁处理。每次提交、验证结论或环境变化后更新。矩阵只保存每仓当前状态索引；命令输出、验证明细和决策放对应章节或 `tmp/` 附件并链接，不重复抄写。

## 10. 维护、修复与清理

### 10.1 接管现有工作区

1. 在两个基座目录的共同父级生成配置，登记 `main` 基座目录下的主 checkout。
2. 不移动主 checkout，不删除历史 worktree，不重建分支维度 worktree。
3. 不改变已有分支、remote、依赖和项目指令。

### 10.2 状态检查与修复

- 用 `git worktree list --porcelain` 和各仓 `git status --short --branch` 建立现状，不凭目录名称判断归属。
- 路径移动后，先核对主 checkout 与 worktree 的实际路径，再执行 `git worktree repair`。
- `git worktree prune` 只清理已确认失效的元数据；执行前列出候选并获得确认，不用 prune 代替故障诊断。

### 10.3 清理分支工作区

- 用户必须明确指定待清理的分支目录；不得按分支名批量匹配清理。
- 清理前逐仓确认没有未提交改动、未跟踪文件和未推送提交；无法证明时停止并列出差异。
- 默认使用 `git worktree remove`，不使用 `--force`，不自动删除 Git 分支。遇到 locked worktree 时停止，不解锁、不强删。
- 默认保留含 `tmp/` 的分支目录。只有用户确认归档位置且归档校验通过后，才可移除原始 `tmp/`。
- 清理后复查 `git worktree list`、目标路径和 `tmp/`；只有确认目录为空后才删除空目录。
- `clean`、`reset --hard`、强制删除分支均属于独立高风险动作，必须单独确认。

## 11. 部署前 CI/CD 实现追踪

用户要求部署、推进或给出 test、UAT、生产环境的部署入口时，必须自动对每个目标仓库分别执行只读 CI/CD 追踪。不得跨仓套用结论，也不得因为仓库中常见某个分支名或 tag 名，就直接认定其部署用途。

### 11.1 追踪顺序

1. 读取项目指令声明的 CI/CD 入口；未声明时检查实际存在的 `.gitlab-ci.yml`、`.github/workflows/`、`Jenkinsfile` 和部署目录。仍无法定位入口时停止并询问。
2. 沿本地 include、模板、可复用 workflow、部署脚本和环境校验脚本继续追踪，直到目标环境 job 的真实执行与判定逻辑。
3. 确认目标环境的触发事件、分支或 tag 匹配规则、目标 ref、手动门禁、版本校验、所需变量及实际部署动作。
4. 核对这些规则所在的 CI 配置版本与待部署 commit；若目标 ref 上的实现不同，必须继续读取目标 ref 版本，不能用当前分支的配置代替。
5. 逐仓输出环境、CI 文件与行号、job、触发条件、目标 ref、手动门禁、证据和未解决项。涉及变量时只记录名称，不输出凭据值。

追踪阶段只读取文件和 Git 对象，不 source、不执行部署脚本、不触发 pipeline。无法静态求值的 expressions 或 variables 必须标为未解决。远程 include 需记录 URL、ref 和可获得的 commit；可变 ref 无法固定、远程内容不可访问或外部脚本缺失时，不得声称已完全证明部署行为。只读追踪不等于授权访问集群、凭据或部署环境。

### 11.2 部署纪律

- 不内置或默认任何 test、UAT、生产分支名、tag 格式、版本规则或环境推进顺序。
- 多个 job 或规则都能匹配目标环境时，列出候选及差异，由用户确认目标。
- CI 配置缺失、实现无法读取、证据冲突或目标 commit 的 CI 版本未核对时，停止部署动作并询问。
- merge、push、打 tag、触发 pipeline 等写操作前，必须另行展示从证据推导出的动作、目标 commit 和环境，并获得用户确认。
- 不得把“找到 CI 文件”当作“已经理解部署方式”；必须追踪到实际控制触发和校验的实现。

## 12. 错误处理与回报

所有写操作遵循以下回报结构：

1. 阻塞项与冲突。
2. 已完成项及可核对路径。
3. 跳过项及原因。
4. 下一步动作及需要用户提供的信息。

禁止把部分成功报告为全部完成。禁止在无法访问目标路径、无法解析配置或缺少仓库 URL 时使用个人路径和远端补齐。

## 13. 验证设计

技能改造按文档 TDD 执行：每个场景使用全新上下文，先在不加载技能的控制组记录失败，再加载技能用同一输入复测。纪律场景加入时间压力、用户坚持惯例和已有沉没成本，验证规则不会被绕过。

### 13.1 基线场景

- 在没有配置的新目录要求首次初始化。
- 用户只提供 `main` 基座目录，尚未提供或确认 `WorkTree` 基座目录。
- 在任意非项目专属目录要求接管两个现有仓库。
- 配置只有部分仓库存在，且一个目标路径不是 Git 仓库。
- 配置含 YAML 重复键、未知字段、规范化后重复的仓库路径、秘密凭据或符号链接逃逸。
- 仓库 `path` 为 `tmp`、`.git` 或 `.branch-worktree`。
- 分支名为 `../../escape`、目标分支已在其他 worktree 检出，或分支目录与另一分支工作区形成父子嵌套。
- 仓库存在多个 remote，或 fetch 已选 remote 失败。
- 主 checkout 当前分支偏离 `defaultBranch`。
- 清理目标包含未提交改动、未跟踪文件、未推送提交或 locked worktree。
- 两个仓库分别使用 `main` 和 `master`。
- 两个仓库使用不同部署方式：一个由分支 push 触发，另一个由 tag 和手动 job 触发。
- CI 入口通过 include 和部署脚本间接决定环境分支及校验规则。
- 当前分支与目标 ref 的 CI/CD 实现不同。
- 远程 include 使用可变 ref、无法访问，或动态 expressions 无法静态求值。
- 在工作区子目录再次执行初始化和分支初始化。

记录是否出现个人路径回退、未经确认的写操作、错误部署假设、重复 clone 或遗漏冲突。前置校验失败场景必须断言没有目录、配置、fetch、worktree 或部署写入；fetch 失败场景必须断言没有继续创建 worktree。

### 13.2 改造后通过条件

- 第一次使用且没有配置时，必然先出现 `main` 与 `WorkTree` 基座目录提醒及用途说明。
- 用户未指定或确认任一基座目录，或者未确认推导结构时，不产生任何写操作。
- 两个基座目录同级，新目录只在用户确认的共同父级工作区内写入。
- 分支开发目录统一位于 `<workspace>/<worktreeDir>/<branch>/`。
- 接管操作不改变已有 checkout 的分支、remote 和内容。
- 重跑无重复 clone、无重复 worktree、无配置差异。
- 非 Git 冲突被保留并显著报告。
- 非法配置、非法分支名和路径逃逸在任何写操作前被拒绝。
- 已有分支不被 reset 或 rebase，已在其他 worktree 检出的分支被报告为冲突。
- remote 按规定顺序选择，不默认 `origin`；远端基线记录完整 SHA，fetch 失败后不创建 worktree。
- 主 checkout 基线漂移只被记录，不切换分支，也不把其 HEAD 当作默认基线。
- 含未提交、未跟踪或未推送成果的清理任务停止并列出差异；locked worktree 不解锁，原始 `tmp/` 默认保留。
- 每个仓库独立形成部署结论，证据来自其目标 commit 的 CI/CD 文件、include 和脚本，不跨仓套用，也不从分支或 tag 名称猜测。
- CI 证据缺失、冲突、版本未核对、动态规则未解决或可变远程 include 未固定时停止部署动作。
- 未提供项目规则时不出现特定服务和客户端命名要求。
- 分支初始化使用配置解析出的同一工作区根目录。
- 技能仓库扫描不到个人绝对路径、个人标识、组织专属仓库名、服务名和内部部署规则。

### 13.3 结构与文字验收

- 首版 frontmatter 只使用 `name` 和 `description`，且 `description` 只写触发条件。
- 所有相对链接的目标存在，参考文件加载条件与入口路由一致。
- `workspace-config.yaml` 的字段、必填性和保留值与第 6 节完全一致。
- `branch-readme.md` 的状态枚举与第 9.1 节一致。
- 同一流程只在一个参考文件中维护完整规则，其他文件只保留链接。
- 每条操作规则都明确触发条件、执行动作和停止条件；删除没有判据的“按需、合理、尽量、默认即可”等表述。

若后续增加脚本，使用临时目录和本地 bare Git 仓库做真实集成测试，不依赖线上仓库或凭据。

## 14. 实施边界

先交付配置模板、技能分层和确定性操作流程。只有这些规则经场景验证稳定后，才考虑把重复命令固化为脚本。任何新增脚本都属于后续独立设计，不在本次隐式扩展。

技能仓库使用 `main` 分支。本阶段只提交设计文档，不创建技能实现文件；实施与验证通过前不推送远端。
