Agent Multi-Repository Worktree

main 是基座，WorkTree 是现场，
tmp 是本次需求的证据。

一次需求只占用一个分支目录。代码改动留在 worktree，验证、决策与交接材料放进 tmp/；tmp/README.md 把每一个改动展开成可复核的事实。

一次需求 一个分支名 一个独立目录 一份可交接记录
01

三层目录，各司其职

目录不是装饰，而是把“基线、改动、证据”从物理上分开，减少互相污染和口头解释。

BASELINE

main/ · 共同基座

存放所有项目的主分支 checkout，用来核对版本、基线和线上问题的起点。

  • 不在里面直接做功能开发
  • 不随意切换分支或重置
  • 开发 worktree 以它为参照
WORKSPACE

WorkTree/ · 隔离现场

每个需求一个目录，里面放本次涉及的各个仓库 worktree。

  • 代码、依赖、服务独立
  • 多个需求可以并行
  • 改动不会串到别的需求
EVIDENCE

tmp/ · 本次需求的产物

不属于业务代码，但属于这次需求本身：过程记录、验证输出和交接材料都放这里。

  • 只服务当前分支目录
  • 不跨需求共享
  • 清理前先归档和校验
<workspace>/
├── main/                          # 所有项目的主分支 checkout，作为基座
│   ├── repo-a/
│   └── repo-b/
├── WorkTree/
│   └── feature-a/                 # 一次需求 = 一个分支名 = 一个目录
│       ├── repo-a/                # 本次涉及仓库的 worktree
│       ├── repo-b/
│       └── tmp/                   # 本次需求的产物，不属于业务代码
│           ├── README.md          # 总览与改动索引
│           ├── change-01.patch
│           ├── verify-01.log
│           ├── decisions.md
│           └── sql/
└── .branch-worktree/
    └── config.yaml                # 工作区配置，不写死个人绝对路径

不要把 tmp 当成全机器共用的临时目录。它属于当前需求的分支目录；另一个需求有自己的 tmp/，两者不要互相复制“看起来差不多”的验证结果。

02

tmp：本次需求留下的完整现场

代码提交回答“改了什么”，tmp/ 还要回答“为什么这样改、怎么验证、遇到什么、下一步谁做”。

README.md
需求目标、仓库矩阵、改动索引、当前状态、阻塞和下一步。
*.patch / diff
关键改动的对照，尤其是需要 reviewer 重点看的片段。
verify-*.log
测试、构建、静态检查的原始输出，标明命令和对应 commit。
scripts/
复现问题、批量校验或联调用的脚本，注明用途和运行条件。
sql/
查询、对比或数据订正语句；默认只读，写操作单独标注。
screenshots/
页面或图表的前后对比，文件名带上场景和版本。
decisions.md
关键选择、被排除的方案和原因，避免下一位接手者重复试错。
pending-evidence.md
尚未取得的证据，明确缺失命令、负责人和所需结果。

tmp 的价值是“可回看”，不是“看起来做了很多”。文件名要能说明来源，内容要能定位到 commit 或命令；不要把大段日志直接塞进 README，链接到具体文件即可。

安全边界：不把密码、token、私钥、生产凭据写进 tmp/；不跨需求复用验证结果；清理 worktree 前默认保留 tmp/，只有归档并校验通过后才移除原文件。

03

README：把每个改动放大

不是流水账，也不是 commit 列表的复读机。每一条改动都要能从“一句话”展开到“可复核的证据”。

一句话摘要这次需求最终改变了什么
→
逐仓改动卡片哪个仓库、哪个 commit、影响哪些范围
→
原始证据链接日志、diff、SQL、截图和验证命令
放大项要回答的问题落在哪里
改了什么用一句话说明行为变化，不写空泛的“优化代码”README 改动索引
为什么改对应的 bug、需求、约束或事故结论改动条目 + decisions.md
影响范围涉及仓库、接口、用户路径、数据或部署单元仓库矩阵
改动前 / 改动后关键代码或行为对比，必要时链接 patchpatch / diff 文件
验证跑了什么命令、在哪个目录、结果如何verify-*.log
commit完整 SHA，和这条改动一一对应README 改动条目
阻塞 / 下一步还缺什么、谁处理、什么条件下继续README 顶部状态区
 
### 2026-11-02 · repo-a · fix: retry failed upload

改了什么  上传失败后最多重试 2 次，避免一次性网络抖动直接失败
为什么改  事故 #4812：上传超时被误判为业务失败，用户看到空结果
影响范围  文件上传接口；不改变请求参数和返回结构
改动前  首次失败立即抛出异常
改动后  仅对可重试错误重试，最终失败仍返回原错误
验证  go test ./upload/... → 18 passed
        [原始输出](verify-01.log)
commit  9f3c2a1d7b6e4f8091a2c3d4e5f60718293a4b5c
风险 / 回滚  重试会延长最坏耗时 2 秒；回滚该 commit 即恢复旧行为

### 2026-11-02 · repo-b · feat: show upload warning

改了什么  上传最终失败时展示可操作的错误提示
为什么改  与 repo-a 的上传错误语义对齐
验证  pnpm test upload → 32 passed
        [原始输出](verify-02.log)
commit  1b2c3d4e5f60718293a4b5c6d7e8f90123456789

“放大”不是把内容写长，而是把证据链补全。摘要让人 30 秒知道结论，条目让人 5 分钟核对一个仓库，链接让人随时回到原始输出。无法验证的部分要明确写成“未验证”，不能补写成成功。

04

这样做，最后得到什么

不是多写文档，而是把返工、误判和重复排查的成本提前消掉。

改动可追溯

每条改动都有原因、范围、commit 和验证输出，不靠记忆解释。

交接可执行

阻塞、负责人和下一步写在同一页，接手者从事实继续，而不是重新猜。

评审更聚焦

reviewer 直接看关键 diff 和验证证据，其余材料按链接展开。

清理更安全

tmp 默认保留；归档、校验、确认后才删除，未推送成果不会被顺手清掉。

目录划分边界，tmp 保存现场，README 放大每一个改动。
这样下一次接手的人，看到的不是一个“大概做完了”的结论，而是一条可以复核的完整路径。
