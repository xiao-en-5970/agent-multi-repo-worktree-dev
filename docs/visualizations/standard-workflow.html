Agent Multi-Repository Worktree

main 是基座，分支目录是现场，
tmp 是本次需求的证据。

一次需求只占用一个分支目录。代码改动留在 worktree，验证、决策与交接材料放进 tmp/；tmp/README.md 把每一个改动展开成可复核的事实。

一次需求 一个分支名 一个独立目录 一份可交接记录
01

三层目录，各司其职

目录不是装饰，而是把“基线、改动、证据”从物理上分开，减少互相污染和口头解释。

BASELINE

main/ · 共同基座

存放所有项目的主分支 checkout，用来核对版本、基线和线上问题的起点。

  • 不在里面直接做功能开发
  • 不随意切换分支或重置
  • 开发 worktree 以它为参照
WORKSPACE

fix/ · feature/ · 隔离现场

每个需求一个目录，里面放本次涉及的各个仓库 worktree。

  • 代码、依赖、服务独立
  • 多个需求可以并行
  • 改动不会串到别的需求
EVIDENCE

tmp/ · 本次需求的产物

位于各仓库 worktree 之外的过程区：验证输出、决策记录和交接文档都放这里。

  • 只服务当前分支目录
  • 不被仓库 Git 跟踪
  • 默认保留，不随 worktree 清理
<workspace>/
├── main/                          # 所有项目的主分支 checkout，作为基座
│   ├── repo-a/
│   └── repo-b/
├── fix/
│   └── upload-retry-20261102/    # 分支目录与 main 并列
│       ├── repo-a/               # 本次涉及仓库的 worktree
│       ├── repo-b/
│       └── tmp/                  # 本次需求的产物，位于所有仓库 worktree 之外
│           ├── README.md         # 交接总览 + 仓库矩阵 + 变更日志
│           ├── change-01.patch
│           ├── verify-01.log
│           ├── decisions.md
│           └── sql/
└── .branch-worktree/
    └── config.yaml               # 工作区配置，不写死个人绝对路径

窄屏可左右滑动，查看完整目录树和表格。

分支名和目录一一对应。fix/upload-retry-20261102 映射为 fix/upload-retry-20261102/，直接位于工作区根目录。用户自己指定的分支名原样尊重；只有用户没指定时，才默认建议 feature|fix|hotfix/<slug>-YYYYMMDD。

默认根级布局：worktreeDir 为 .，分支目录和 main 并列，不额外建 WorkTree 层；分支路径必须避开 main 和已登记仓库。只有项目明确选择独立 worktree 目录时，才把 worktreeDir 指向该目录。

目录名以配置为准。main/ 是本文示例；实际名称来自用户首次确认的 mainDir。分支目录由分支路径直接生成，不再有固定的 WorkTree/ 层。

tmp 不是 IDE 或构建临时目录。它位于 <branch path>/tmp，在所有仓库 worktree 之外，因此不被任何仓库 Git 跟踪；也不是仓库内部被 .gitignore 忽略的 tmp/。另一个需求有自己的 tmp/，不要互相复制验证结果。

02

tmp：本次需求留下的完整现场

代码提交回答“改了什么”，tmp/ 还要回答“为什么这样改、怎么验证、遇到什么、下一步谁做”。

README.md
按固定骨架记录阻塞、摘要、仓库矩阵、验证证据、下一步、决策和变更日志。
*.patch / diff
关键改动的对照，尤其是需要 reviewer 重点看的片段。
verify-*.log
测试、构建、静态检查的原始输出，标明命令和对应 commit。
scripts/
复现问题、批量校验或联调用的脚本，注明用途和运行条件。
sql/
查询、对比或数据订正语句；默认只读，写操作单独标注。
screenshots/
页面或图表的前后对比，文件名带上场景和版本。
decisions.md
关键选择、被排除的方案和原因，避免下一位接手者重复试错。
pending-evidence.md
尚未取得的证据，明确缺失命令、负责人和所需结果。

tmp 的价值是“可回看”，不是“看起来做了很多”。文件名要能说明来源，内容要能定位到 commit 或命令；不要把大段日志直接塞进 README，链接到具体文件即可。

清理默认保留 tmp。不把密码、token、私钥、生产凭据写进 tmp/，不跨需求复用验证结果。只有用户明确要求归档、并单独确认归档目的地后，才创建归档；归档后必须完成归档校验，逐项核对文件清单、相对路径、大小和内容校验和。校验失败则保留原文件，校验通过后才可移除原始 tmp/。

03

README：先交接，再把每个改动放大

tmp/README.md 不是一份纯变更日志。它按 templates/branch-readme.md 的固定骨架先说明阻塞、状态、仓库矩阵和验证证据，再用变更日志把每一项改动展开到可复核的细节。

固定骨架先看阻塞、状态、目标和共用分支
→
矩阵与证据逐仓定位基线和当前 commit
→
变更日志展开每个改动的原因、影响和验证

固定骨架：从阻塞项开始

章节顺序固定。矩阵只保存当前状态索引；完整命令输出和决策材料放到 tmp/ 的独立附件，并在对应章节链接。

顺序固定章节必须写清
1阻塞项受影响仓库、缺失条件、负责人、解除条件；没有阻塞时明确写“无”。
2当前摘要状态、当前阶段和当前事实；状态只能从五种值中选择。
3目标 · 共用分支本次范围和统一的 branch-name。
4仓库矩阵仓库、路径、基线、基线 commit（完整 SHA）、当前 commit（完整 SHA）、状态、当前阶段和验证证据链接。
5验证证据仓库、对应 commit、命令、执行目录、结果和原始输出链接。
6下一步动作、执行者、等待条件；等待用户输入时写出具体问题。
7关键决策日期、结论、备选方案和依据，可链接到附件。
8变更日志日期、变更内容、commit 或证据链接；详细展开见下一节。
未开始进行中阻塞完成不适用

状态只能使用以上五种。当前阶段描述正在做的工作，不是额外状态；标为“完成”必须附证据，标为“阻塞”必须填写缺失条件和负责人。矩阵中每个“验证证据”单元格都必须填写相对 tmp/README.md 的实际链接；证据缺失时链接到写明缺失命令、负责人和所需结果的待补记录，不能留空或编造结果。

变更日志：每个改动如何放大

日志里每一条改动都要能从一句话继续展开，回答下面七项。完整 SHA 写在条目中，验证必须包含命令、执行目录和原始输出。

放大项要回答的问题写在哪里
改了什么具体行为发生了什么变化，不写空泛的“优化代码”变更日志条目
为什么改对应的 bug、需求、约束或事故结论变更日志 + 关键决策
影响范围涉及仓库、接口、用户路径、数据或部署单元变更日志 + 仓库矩阵
改动前 / 改动后关键行为或代码对比，必要时链接 patch变更日志 + tmp 附件
验证命令、执行目录、结果和原始输出，全部对应同一个 commit验证证据表 + 变更日志
commit用完整 SHA 关联改动、矩阵和证据仓库矩阵 + 变更日志
风险 / 回滚最坏影响是什么，如何回滚，是否有未验证部分变更日志条目

“放大”不是把内容写长，而是让每条结论都能回到原始证据。矩阵提供索引，变更日志展开原因、影响和验证，附件保存原始输出。无法验证的部分明确写“未验证”，不得改写成成功。

04

这样做，最后得到什么

不是多写文档，而是把返工、误判和重复排查的成本提前消掉。

改动可追溯

每条改动都有原因、范围、commit 和验证输出，不靠记忆解释。

交接可执行

阻塞、负责人和下一步写在同一页，接手者从事实继续，而不是重新猜。

评审更聚焦

reviewer 直接看关键 diff 和验证证据，其余材料按链接展开。

清理更安全

tmp 默认保留；归档、校验、确认后才删除，未推送成果不会被顺手清掉。

目录划分边界，tmp 保存现场，README 放大每一个改动。
这样下一次接手的人，看到的不是一个“大概做完了”的结论，而是一条可以复核的完整路径。
