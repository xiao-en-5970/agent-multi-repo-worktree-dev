# 分支开发初始化

## 1. 输入与前置条件

配置必须通过 `workspace-init.md` 的校验，所有涉及仓库均已登记并具有有效主 checkout。沿用工作区规则已选择的每仓 remote；不得默认或改选 remote，也不得用主 checkout HEAD 代替远端默认基线。

分支初始化至少需要两项输入：

1. **共用分支名**：所有涉及仓库统一使用该名称。
2. **需求来源**：需求文档链接、任务号或粘贴的需求正文，必须足以判断涉及的服务、仓库、接口或页面范围。

涉及仓库是**可选**输入。用户明确列出仓库时，以该列表为候选并核对配置登记；省略时，从需求文档中的服务名、仓库名、接口/页面范围和变更描述推导候选仓库，列出候选、依据和未纳入项，等待确认。不得仅凭名称相似或“前后端”等泛称猜测，不得把未登记仓库静默加入配置。

确认候选仓库后，再执行下方的基线、路径和占用预检。用户明确要求“前后端联调”时，候选集合应覆盖需求涉及的前端、后端和共享接口仓库；一次创建它们的 worktree 与交接骨架，不要求用户逐仓重复发起。依赖安装、服务启动和部署仍按第 2 节及项目指令单独确认。未登记、需求无法读取或映射有歧义时停止并询问，不自动 clone。

缺少共用分支名或需求来源时先询问；选择已有开发分支作为基线时，该分支必须由用户明确指定。

### 分支命名与目录映射

分支名按以下优先级处理：

1. **用户提供的分支名。** 原样尊重用户名称，不追加日期，不替换前缀，不按团队惯例重写。只执行 `git check-ref-format --branch` 和路径安全检查，并确认所有仓库使用同一名称。用户名称非法或路径不安全时停止并询问，不能静默改名。
2. **用户未提供分支名，或明确要求 Agent 起名。** 提出一个默认名并取得确认；用户确认后才使用。

默认命名规则为：

```text
^(feature|fix|hotfix)/[a-z0-9]+(?:-[a-z0-9]+)*-[0-9]{8}$
```

- 前缀默认使用 `feature`（新功能）、`fix`（缺陷修复）或 `hotfix`（线上紧急修复）。
- `<slug>` 默认只使用小写 ASCII 字母、数字和单个连字符，不得以连字符开头或结尾。
- 尾部 `YYYYMMDD` 必须是**真实日历日期**，表示需求创建日；只有默认命名时才由 Agent 按当前日期补齐，并先展示完整名称供用户确认。
- 用户提供自己的命名风格时，即使不含日期或使用其他前缀，也按用户名称继续，不强制套用上式。

**斜杠始终映射为嵌套目录。** 例如 `fix/upload-retry-20261102` 对应 `WorkTree/fix/upload-retry-20261102/`，`tmp/` 位于该完整分支目录下。自定义名称中的斜杠同样按层级展开，但每一级都必须是非空、非 `.`、非 `..`、不含反斜杠的安全目录名。

`WorkTree/feature/`、`WorkTree/fix/`、`WorkTree/hotfix/` 以及自定义名称的中间层级是**分组目录**，可以同时容纳多个分支目录；只有完整分支路径对应的目录才算分支工作区。完整分支目录与另一个已识别的分支目录形成父级/子级**前缀重叠**时停止；仅作为命名空间的分组目录不触发冲突。

严格按以下顺序执行。任何写入前的停止条件触发时，不创建 `tmp/`、worktree 或分支，不静默改名，不缩小校验范围。写入后发现目标冲突时保留该路径原状，报告冲突及已验证事实。

1. **校验或提出共用分支名。** 用户已提供名称时原样保留，只执行 `git check-ref-format --branch` 和路径安全检查；未提供或用户要求起名时，按默认规则提出带日期的名称并等待确认。非法名称停止并询问，不改名、不截断；所有仓库使用同一分支名。
2. **解析并约束分支目录。** 将分支名按 `/` 分割，逐级映射到 worktree 根：默认布局为 `<workspace>/<worktreeDir>/`，根级布局（`worktreeDir` 为 `.`）为 `<workspace>/`。`branchDir` 是完整分支路径对应的叶子目录，中间层级是允许存在的分组目录。确认 `branchDir` 物理路径位于 worktree 根内，且不与 `mainDir`、`.git`、`.branch-worktree` 重叠；根级布局还必须避开所有已登记仓库路径。完整分支目录与另一个已识别的分支工作区互为**父级或子级**（前缀重叠）时停止；仅作为命名空间的分组目录不算分支工作区。不得自动改名或另选目录。目录不存在时，解析最近现有祖先并校验待创建尾路径。
3. **选择并分类基线。** 明确涉及仓库及各仓基线。默认分支基线取已选 remote 的默认分支完整 commit SHA；已有开发分支必须由用户明确指定。选择非默认分支基线时，先用项目指令或 CI/CD 证据证明它不是部署环境分支；证据不足或冲突时列出候选并询问，不凭名称判断，也不设置默认部署 ref。
4. **记录主 checkout 的同步前状态。** 记录每仓主 checkout 当前分支、当前 commit 和脏状态，本步骤不切换分支、不修改文件。当前分支与 `defaultBranch` 不一致时记录“基线漂移”；是否可同步在第 6 步判断，默认基线始终取已选 remote 的默认分支 commit。
5. **在任何写入前解析全部物理路径。** 对每个 `<branchDir>/<path>` 解析物理路径；目标不存在时解析**最近现有祖先**并校验待创建尾路径。全部结果必须位于 `branchDir` 内，且不得与 `tmp`、`.git`、`.branch-worktree`、其他仓库路径或已有分支工作区重叠。发现符号链接逃逸、保留路径碰撞或父子路径重叠时停止。此阶段同时读取各仓 worktree 列表，完成第 7 步所需的存在性与占用检查；不得等到部分仓库写入后才发现冲突。
6. **确认远端读取并同步主 checkout。** 对需要远端基线的仓库，逐仓展示所选 remote、fetch 命令、fast-forward 计划和用途，获得用户确认后才 fetch；不 fetch 其他 remote。成功后确认目标 ref 并记录其**完整 SHA**，然后按以下规则同步：
   - 主 checkout 干净且位于默认分支：只使用 `git merge --ff-only <selected-remote>/<default-branch>` 快进；已相同则无操作。
   - 主 checkout 脏、位于其他分支、已领先或分叉，或 fast-forward 失败：跳过该仓同步，记录“同步跳过”及原因；不切换分支、不 stash、不 reset、不 rebase、不覆盖本地改动。
   - 同步结果不改变基线来源；基线仍取所选 remote 默认分支的完整 SHA，不得把未同步或有漂移的主 checkout HEAD 当作最新基线。
   - fetch 失败或无法确认完整 SHA 时停止；只有用户明确指定一个具体本地 commit，并确认该 commit 可能过旧后，才可改用该 commit，记录完整 SHA 和确认证据。
7. **全局来源与目标预检。** 在任何 `tmp/`、worktree 或分支写入之前，解析并分类每个仓库的本地分支和所选 remote 的同名分支来源，记录各自的完整 SHA，并同时解析现有目标及占用状态（目标 worktree 的实际路径和分支、同名分支是否已在其他 worktree 检出）。仅当本地与所选 remote 的 ref 解析为完全相同的完整 SHA 时才去重，作为一个无歧义来源；本地与所选 remote 的完整 SHA 不同即为分歧。分歧、多个来源或目标歧义，以及任何目标冲突，均全局停止整个初始化，不得开始任何仓库写入，不按日期、名称或惯例选择。无歧义时保持既有来源优先级：本地分支优先于所选 remote 的同名分支；二者均不存在时才从已确认的默认基线新建。已有分支不 reset、不 rebase。
8. **校验通过后写入。** 先创建 `branchDir/tmp/`，再逐仓只按以下顺序处理，并把选定来源的完整 SHA 作为基线记录：
   - 目标 worktree 已存在：核对实际路径和分支一致后跳过，记录证据；不一致则报冲突，不覆盖。
   - 分支已在其他 worktree 检出：报冲突并停止分支初始化，禁止后续任何写入；保留所有已有路径原状，报告冲突及已验证事实，不重复检出、不移动其他 worktree。
   - **本地分支**存在：使用其当前 commit，不重置。
   - **所选 remote** 存在唯一同名分支：使用该远端分支已确认的 commit。
   - 本地与所选 remote 均不存在同名分支：从已确认的默认基线新建。
   - 存在多个匹配或来源有歧义：停止并询问，不按日期、名称或惯例选择。
9. **保留已有历史。** 已有分支**不 reset**、**不 rebase**；不得通过删除、移动或重建分支绕过冲突，不得静默重命名分支或在不同仓库使用不同分支名。
10. **交接与回报。** 按 `handoff.md` 创建 `tmp/README.md`，填实仓库矩阵、基线 commit、当前 commit、状态和下一步。回报阻塞与冲突、成功项、跳过项、各仓 commit 和验证证据；附可核对路径。存在冲突、跳过或待确认项时不得声称全部完成。

## 2. 附加动作边界

只有工作区指令、仓库指令或用户明确要求时，才执行依赖安装等附加动作；执行前说明命令、目录和影响并取得确认。本流程不执行部署，不推断部署分支或 tag。
