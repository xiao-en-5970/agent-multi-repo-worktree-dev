# 基于证据的部署发现

收到部署、环境推进或部署入口请求时，对**每个目标仓库**分别做只读静态追踪。不得跨仓套用结论，不得从常见分支名、tag 名或目录名推断部署用途。

## 追踪步骤

1. 先读项目指令声明的 CI/CD 入口；未声明时，检查实际存在的 `.gitlab-ci.yml`、`.github/workflows/`、`Jenkinsfile` 和部署目录。仍无法定位时，停止并询问。
2. 沿本地 `include`、模板、可复用 workflow、部署脚本和环境校验脚本逐层追踪，直至目标环境 job 的实际执行与判定逻辑。发现脚本不等于理解脚本；找到 CI 文件也不等于证明部署行为。
3. 记录目标环境的触发事件、分支或 tag 匹配规则、目标 ref、手动门禁、版本校验、所需变量名称和实际部署动作。
4. 核对上述实现与**目标 commit** 的 CI 版本。当前分支与目标 ref 不同或实现可能不同时，必须读取目标 ref 对应 commit 的配置、include 和脚本，不得以当前分支版本代替。
5. 逐仓输出下表；每条结论附实际文件名和**行号**，变量只记名称，不输出凭据值。

| 仓库 | 环境 | 目标 commit | CI 文件与行号 | job | 触发条件 | 目标 ref | 手动门禁 | 版本校验 | 变量名称 | 实际部署动作 | 未解决项 |
|---|---|---|---|---|---|---|---|---|---|---|---|

## 只读边界与未解决项

- 追踪只读取文件和 Git 对象：**不 source**，**不执行部署脚本**，不触发 pipeline，也不以只读追踪为由访问集群、凭据或部署环境。
- 无法静态求值的 `expressions`、无法读取的变量、无法固定的**可变 ref**、不可访问的远程内容、缺失的外部脚本，以及相互矛盾的规则，全部标为“未解决”。不得猜测其取值或行为。
- 远程 include 记录 URL、ref 和可获得的 commit。对可变 ref 做一次性远端解析不能消除未解决状态；只有目标 commit 所需内容已固定到不可变版本且实际读取后，才可关闭相应未解决项。
- CI 配置缺失、实现无法读取、证据冲突、目标 commit 的 CI 版本未核对，或任一必要规则未解决时，停止部署动作并询问，不声称已完全证明部署行为。
- 多个 job 或规则可能匹配同一环境时，列出候选及证据差异，请用户确认，不自行选择。

## 部署写操作纪律

- **不默认**任何环境分支名、tag 格式、版本规则或环境推进顺序；只采用目标 commit 证据明确支持的规则。
- 证据完整且未解决项清空前，不给出任何部署写操作指令，包括命令模板。
- 即使证据完整，merge、push、打 tag、触发 pipeline 也分别属于独立写操作；执行前逐项展示由证据推导出的动作、目标 commit 和目标环境，并取得用户**单独确认**。发现阶段的许可不等于写操作许可。
